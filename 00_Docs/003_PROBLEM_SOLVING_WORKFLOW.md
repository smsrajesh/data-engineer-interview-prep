# 💻 Problem Solving Workflow

> **"Don't practice until you get it right. Practice until you can't get it wrong."**

This workflow is designed to help you develop the thinking process used by professional software engineers during coding interviews and real-world problem solving.

The goal is not just to solve problems.

The goal is to understand problems, write better solutions, recognize patterns, and become a stronger engineer.

---

# 🎯 Purpose

This workflow helps you:

- Think independently before looking at solutions.
- Develop strong analytical skills.
- Write clean and efficient code.
- Learn optimization techniques.
- Connect coding problems to Data Engineering.
- Build confidence for technical interviews.

Every coding problem in this repository follows this workflow.

---

# 🟢 Phase 1 — Problem Solving

> **Mindset:** *"Can I solve this problem on my own?"*

The first phase focuses on understanding the problem and developing your own solution before receiving any guidance.

---

## Step 1 — Read the Problem

Read the problem carefully.

Understand:

- What is the input?
- What is the expected output?
- What are the constraints?
- Are there any hidden edge cases?

Do not start coding immediately.

Spend a few minutes understanding the problem.

---

## Step 2 — Write Your Solution

Write your own solution.

Even if you think it is wrong, write it.

> **A wrong solution teaches more than copying the correct one.**

Do not search for hints unless you are completely stuck.

---

## Step 3 — Test Your Solution

Before running your code, think of at least **3–5 test cases**.

Try to include:

- Normal cases
- Edge cases
- Boundary cases
- Empty input
- Large input

If you cannot think of enough test cases, ask:

> **"Give me edge cases only."**

This encourages independent thinking while still providing guidance.

---

## Step 4 — Analyze Your Solution

Before moving on, answer these questions.

- What is the time complexity?
- What is the space complexity?
- Can this solution be optimized?
- Where might this solution fail?

These are common interview follow-up questions.

---

# 🔵 Phase 2 — Engineering Excellence

> **Mindset:** *"Can I improve this solution?"*

Now we shift from solving the problem to improving the quality of the solution.

---

## Step 5 — Code Review

Your solution is reviewed like it would be in a technical interview.

The review focuses on:

- Logic
- Correctness
- Edge cases
- Time complexity
- Space complexity
- Code readability
- Variable naming
- Python coding style
- Interview expectations

The goal is constructive feedback, not just finding mistakes.

---

## Step 6 — Optimization Discussion

Before seeing the optimal solution, ask yourself:

> **"Can I make this solution better?"**

If you're unsure, receive hints first.

The optimal solution should be the last thing you see, not the first.

---

## Step 7 — Study the Optimal Solution

Now compare your solution with the optimized approach.

Focus on understanding **why** it is better.

Compare:

| Time Complexity | | |
| Space Complexity | | |
| Readability | | |
| Scalability | | |
| Edge Cases | | |

Understanding the differences is more valuable than memorizing the code.

---

## Step 8 — Pattern Recognition

Every coding problem belongs to one or more patterns.

Examples include:

- Hash Map
- Two Pointers
- Sliding Window
- Binary Search
- Stack
- Queue
- DFS
- BFS
- Dynamic Programming

Instead of remembering problems, learn to recognize patterns.

This is one of the most valuable interview skills.

---

# 🟣 Phase 3 — Professional Growth

> **Mindset:** *"How is this used in real-world engineering?"*

Coding problems are not isolated exercises.

Most of them represent real engineering challenges.

---

## Step 9 — Data Engineering Connection

Understand where the pattern appears in Data Engineering.

Examples:

| Coding Pattern | Data Engineering Application |
|----------------|------------------------------|
| Sliding Window | Streaming analytics |
| Hash Map | Deduplication and lookups |
| Sorting | ETL transformations |
| Prefix Matching | Log and file parsing |
| Graph | Airflow DAG dependencies |
| Heap | Top-N analytics |
| Queue | Message processing |
| Binary Search | Partition lookup |

Connecting interview questions to production systems strengthens long-term understanding.

---

## Step 10 — Git Practice

Every completed problem should include a professional Git commit.

Example:

```text
feat(strings): solve longest substring without repeating characters using sliding window

- Implement sliding window optimization
- Handle edge cases
- Analyze time and space complexity
- Add interview discussion
```

Writing meaningful commit messages is a valuable professional habit.

---

## Step 11 — Reflection

Take two minutes to reflect.

Ask yourself:

- What did I learn?
- What mistake did I make?
- What pattern did I discover?
- Where else can I apply this idea?
- Could I explain this solution to someone else?

Reflection transforms practice into understanding.

---

# 🏁 Success Checklist

Before marking a problem as complete, ensure that you can confidently answer:

- [ ] Can I explain the problem?
- [ ] Can I explain my solution?
- [ ] Can I analyze the complexity?
- [ ] Can I identify the pattern?
- [ ] Can I connect it to Data Engineering?
- [ ] Can I explain it like an interviewer expects?

If every answer is **Yes**, the problem is complete.

---

# 🌟 Final Thought

Great engineers are not defined by the number of problems they solve.

They are defined by the depth of understanding they gain from every problem.

> **"Don't collect solutions. Build intuition."**
